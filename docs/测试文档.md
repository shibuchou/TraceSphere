## 1. 文档说明

### 1.1 目的

本文说明 TraceSphere 的测试范围、测试环境、测试方法、用例、执行记录、缺陷和已知限制。测试结论以 `docs/evidence/` 中保存的原始报告为准；本文只引用已落盘的结果，不把设计目标写成实测结论。

### 1.2 测试对象

| 模块 | 代码 | 测试重点 |
|---|---|---|
| platform | `platform/` | 事件归一化、身份补全、资源图、关联簇、证据、HTTP API、ZSvirt REST Provider |
| rca | `rca/` | 规则加载、证据匹配、Evidence Match 评分、诊断 API、CLI、fixture 回放 |
| console | `console/` | 类型契约、夹具一致性、CSS 模块引用、四个页面与交互 |
| vm-agent | `vm-agent/` | eBPF / PSI / cgroup / OOM 日志采集、降级、上报与 spool |
| workload | `workload/` | 样例 Agent 链路、四类故障注入、Prometheus 抓取、Mock DCGM |
| 部署与运维 | `deploy/`、`tools/` | systemd 常驻、一键起停、验收、重置、脱敏 |

### 1.3 依据

- [方案说明](方案说明.md)：数据模型、采集方式、关联逻辑、告警策略、降级要求；
- [RCA 接口契约](../rca/docs/API.md)：规则结构、证据模型、五维评分、HTTP API；
- [平台接口说明](../platform/README.md)：`/api/v1` 契约；
- [部署文档](部署文档.md)：环境、配置与验证步骤；
- `rca/internal/engine/engine_test.go`：Top-1 回归阈值；
- `docs/evidence/`：四场景验收、证据链、探针开销、真实环境运行记录。

### 1.4 测试数据源标记

每个诊断响应都带 `source` / `sources`：

| 标记 | 含义 |
|---|---|
| `real` | 真实数据源（ZSvirt / Prometheus / vm-agent / AppEvent） |
| `degraded` | 数据源可用性下降，部分证据缺失 |
| `mock` | fixture 回放或 Mock DCGM 模拟数据 |
| `off` | 未启用 |

测试结论必须同时记录数据源标记。`fixture=off` 的真实演练结果与 `fixture=mock` 的回放结果分开统计。

## 2. 质量目标与准入标准

### 2.1 功能目标

| 编号 | 目标 | 验收口径 |
|---|---|---|
| G-01 | 四类受控故障 Top-1 命中 | Case1 `container_oom`、Case2 `cpu_contention`、Case3 `tool_failure`、Case4 `gpu_memory_exhaustion` |
| G-02 | 诊断可解释 | 每次诊断输出 5 个评分维度、证据 ID、影响范围、处置建议（依据 / 操作 / 风险） |
| G-03 | 证据可追溯 | 每条证据有 `evidence_id` 与 `source_event_ids`；诊断引用证据 ID |
| G-04 | 无证据不诊断 | 空证据返回 0 条候选，不按规则硬报 |
| G-05 | 真实 / 回放可区分 | 页面角标与页脚显示数据源；api 模式失败不静默降级 |
| G-06 | 降级可用 | 无 GPU 用 Mock DCGM；无 eBPF 保留 PSI/cgroup；平台不可用可 fixture 回放 |
| G-07 | 安全基线 | Token、限流、字段白名单、控制面回环绑定、凭据不入库 |
| G-08 | 低侵入 | vm-agent idle CPU < 2%、RSS < 100 MiB（设计目标） |
| G-09 | 可复现 | 四场景 fixture 可在无云环境回放，结果与现场一致 |

### 2.2 准入门槛

发布 / 提交前必须满足：

1. `platform` 50 项单测全部通过；
2. `rca` 的 `go test ./...` 全部通过，四场景 Top-1 不低于回归阈值；
3. `console` 的 `npm run verify` 通过，`npm run build` 成功；
4. `tools/acceptance.sh` 四场景产出报告，Top-1 正确；
5. 安全基线检查通过（见 §9）；
6. 提交包脱敏与残留扫描结果为 `clean`。

### 2.3 回归阈值

`rca/internal/engine/engine_test.go` 当前阈值：

| 场景 | 期望 Top-1 规则 | 评分下界 | 期望时间线层级 |

| case2-cpu | `cpu_contention` | 75 | vm |
| case3-tool-failure | `tool_failure` | 60 | application |

阈值是“真实抓取 fixture 的实测下界”，不是满分要求。最近一次实测值为 99 / 85 / 67 / 89，均高于阈值。

## 4. 测试策略

### 4.1 分层

| 层级 | 对象 | 方法 | 执行方式 |
|---|---|---|---|
| L1 单元测试 | platform 的 schema / store / ingest / correlate / REST provider / mock GPU | Python `unittest`，临时 SQLite 与 fake provider | 自动 |
| L1 单元测试 | RCA 的规则加载、评分、fixture 诊断 | Go `testing`，fixture 回放 | 自动 |
| L2 契约测试 | 事件三种格式、证据 signal 命名、API 响应字段 | 单测 + fixture 校验 | 自动 |
| L2 前端契约 | 类型定义与 `API.md` 一致、夹具字段完整 | `tsc --noEmit` + `check-fixtures` + `check-css` | 自动 |
| L3 集成测试 | ZSvirt REST → platform → 资源图 → 事件 → 关联 → 证据 | 真实环境 / fixture | 自动 + 手工 |
| L4 端到端验收 | 注入 → 采集 → 入库 → 关联 → RCA → Console | `tools/acceptance.sh` + 页面核对 | 半自动 |
| L5 安全测试 | Token、限流、绑定、字段白名单、隐私 | curl + 代码审查 + 配置核对 | 手工 |
| L6 性能测试 | vm-agent 开销 | `measure-overhead.sh` 采样 | 手工 |
| L7 降级测试 | 无 GPU / 无 eBPF / 平台不可用 / fixture | 关闭数据源或切场景 | 手工 |
| L8 UI 测试 | 四页面、筛选、状态操作、错误态 | 浏览器手工核对 | 手工 |

### 4.2 测试判定

- **Top-1 正确**：规则 ID 与预期一致；
- **评分合理**：不低于回归阈值，且 `score_breakdown` 五维齐备；
- **证据可溯**：`evidence_ids` 非空，证据可在响应中逐条找到；
- **影响范围非空**：`impact.scope` 至少包含一个资源；
- **时间线非空**：至少包含预期层级的证据；
- **来源正确**：真实演练 `fixture=off`；回放 `fixture=mock`；
- **无证据不诊断**：空快照返回 0 条候选。

## 7. 端到端场景验收

### 7.1 验收流程

`tools/acceptance.sh` 对每个场景执行：

1. `reset-platform.sh` 清空平台数据库，获得干净基线；
2. 重启 vm-agent，确认直报就绪；
3. 在业务 VM 内注入故障；
4. 通过 `faults/run-task.sh` 触发一次 Agent 任务，拿到 `correlation_id`；
5. 恢复故障；
6. 等待事件入库，查询 platform health 的 counts；
7. `POST /api/v1/correlate` 执行关联；
8. `tracesphere diagnose --correlation-id <corr> --window 10m` 输出诊断报告；
9. `tracesphere capture` 把真实数据写回 `rca/fixtures/`。

### 7.3 E2E-01 容器 OOM

**前置**：platform / RCA / vm-agent / workload 全部就绪；`tool-service` 正常运行。

**步骤**：

```bash
# 1) 收紧 tool-service 内存
sudo docker update --memory=8m --memory-swap=8m tool-service
# 2) 触发任务
bash /opt/tracesphere/workload/faults/run-task.sh 'OOM 演练任务 - 期望工具调用失败'
# 3) 恢复
cd /opt/tracesphere/workload && sudo docker compose up -d --force-recreate tool-service
```

**期望**：内核 OOM 事件、容器重启、`task.failed`；Top-1 为 `container_oom`。

**实测（2026-09-30，correlation_id `bb03e1b2c022`）**：

- 时间窗：2026-09-30T14:04:26Z ~ 14:14:26Z（600s）；
- 证据 34 条；
- Top-1 `container_oom`，99/100；
- 评分明细：规则证据命中 55/55（4/5 条：`memory.events.oom_kill`、`oom.ebpf`、`task.failed`、`container.restart`）；时间优先性 15/15（`task.failed` 晚于 OOM 10.0s）；资源邻接度 9.4/10；信号强度 10/10；独立证据数 10/10（app_event / cgroup / ebpf / metric 四类）；
- 证据示例：`memory.events.oom_kill`（cgroup，value=7）、6 条 `oom.ebpf`、2 条 `task.failed`、`container.restart`（metric，value=1）。

**结论**：通过。该场景同时具备容器层内核证据与应用层失败证据，是四场景中证据最完整的一条。

### 7.4 E2E-02 CPU 争抢

**注入**：

```bash
bash /opt/tracesphere/workload/faults/cpu.sh
sudo docker update --cpus=0.5 llama-server
```

**期望**：PSI `cpu.some` 升高、`cpu.cfs.throttled_periods` 递增、任务超时；Top-1 为 `cpu_contention`。

**实测（2026-09-30，correlation_id `e40e7ba37a41`）**：

- 时间窗：14:07:12Z ~ 14:17:12Z（600s）；
- 证据 28 条；
- Top-1 `cpu_contention`，85/100；

### 7.7 评分归一化说明

Evidence Match 是**规则证据命中评分**，不是概率，也不做概率校准。总分按“适用维度”归一化：

```text
match_score = min(100, Σ各维度得分 / Σ适用维度上限 × 100)
Σ适用维度上限 = 55 + (规则有 after ? 15 : 0) + 10 + 10 + 10
```

因此：

| 场景 | 维度得分和 | 适用上限 | 展示分 |
|---|---:|---:|---:|
| Case1 | 55 + 15 + 9.4 + 10 + 10 = 99.4 | 100 | 99 |
| Case2 | 45.3 + 0 + 9.2 + 8 + 10 = 72.5 | 85 | 85 |
| Case3 | 32.4 + 15 + 10 + 8 + 2 = 67.4 | 100 | 67 |
| Case4 | 55 + 0 + 10 + 9 + 2 = 76 | 85 | 89 |

Case2 / Case4 的规则没有 `after` 时序约束，时间优先性维度 `max=0`，不参与归一化；所以子项之和看起来低于总分，这是设计行为，不是计算错误。

| 资源图 | SQLite 边表 + 浅层 BFS（关联 1 跳、影响范围 depth=2），不是图数据库，没有多跳传播 |
| 日志与追踪 | 没有 Fluent Bit / Loki 日志管道；没有分布式追踪；`trace_id` 列存在但无生产者 |
| 告警 | 没有部署 Alertmanager；现有能力是“多事件 → 关联簇 → 一条告警”的自研聚合与三态运营（open / acknowledged / resolved + silenced） |
| ZSvirt 只读 | 由代码不调用写接口保证；实际账号为 `admin`，没有受限账号验证 |

### 14.2 覆盖缺口

- 没有真实 GPU / vGPU / DCGM exporter 环境；
- 没有 Kubernetes / 多集群 / 多租户；
- 没有生产级 HA、SQLite 多写、RCA 多实例；
- 没有长时间稳定性 / 内存泄漏 / soak 测试；
- 没有大规模事件压测与查询性能测试；
- 没有自动化浏览器 E2E、无障碍、跨浏览器测试；
- 没有升级 / 回滚自动化测试；
- 没有网络分区、磁盘满、数据库损坏等故障演练；
- 没有对 ZSvirt 不同版本的兼容矩阵，只在 v1.0.0 上验证。

### 14.3 材料表述约束

- Evidence Match 是证据命中评分，不是概率、不是准确率；
- `health_score` 是展示分，不参与 RCA；
- 四场景结果是受控故障下的结果，不是通用准确率；
- 不能把“设计目标”写成“实测结果”；
- 不能把 Mock DCGM 写成真实 GPU 验证；
- 不能把自研告警聚合写成 Alertmanager 能力。
