# TraceSphere 用户手册

> 面向 ZSvirt 虚拟机内容器与智能体工作负载的全栈可观测平台
> 上海开源软件应用创新大赛 · 基于 ZSvirt 虚拟化平台
> 文档版本：v1.0（2026-10-27）｜ 适用版本：TraceSphere v0.1

---

## 1. 文档说明

### 1.1 适用读者

| 读者 | 关注内容 |
|---|---|
| SRE / 平台运维 | 拓扑、健康、告警、证据链、处置建议 |
| Agent / 应用研发 | 任务失败原因、工具调用错误、推理异常 |
| 评测 / 演示人员 | 数据源标识、演示路径、四场景切换 |
| 自动化脚本作者 | CLI、HTTP API、fixture 回放 |

### 1.2 你会得到什么

TraceSphere 回答一个问题：

> **某个 Agent 任务的一次失败，究竟由应用、容器、虚拟机、GPU 还是宿主机引起？**

它把 ZSvirt 资源、VM 内系统信号、Prometheus 指标、Agent 应用事件放进同一条证据链，给出：

- 根因候选 Top-N（按 Evidence Match 排序）；
- 每个候选的五维评分明细；
- 可逐条追溯的证据 ID；
- 受影响资源与任务；
- 带“依据 / 操作 / 风险”的处置建议。

## 2. 访问与登录

### 2.1 打开 Console

部署完成后访问：

```text
http://<PLATFORM_IP>:8010/
```

默认路由会跳转到 `/health`（健康总览）。

### 2.2 鉴权

Console 没有用户名 / 密码体系，只支持静态 Token：

- 若部署时未设置 `TRACESPHERE_RCA_TOKEN`，直接打开即可；
- 若设置了 Token，第一次访问使用：

```text
http://<PLATFORM_IP>:8010/?token=<RCA_TOKEN>
```

页面会把 Token 写入浏览器 `localStorage` 的 `tracesphere.auth_token`，后续请求自动带 `Authorization: Bearer`。Token 会留在地址栏，演示前建议重新打开不带 `?token=` 的地址。

Token 失效或被清除时，页面会显示 401 错误；重新用 `?token=` 打开即可。

### 2.3 浏览器与网络

- 推荐 Chrome / Edge 最新版本；
- Console 需要访问同源的 `/api/v1`；若由 RCA 托管，通常无需额外配置；
- 若通过 Nginx / 网关访问，需把 `/api/v1` 反向代理到 RCA 的 8010；
- 页面时间统一显示 UTC，与 ZSvirt / 平台日志一致。

## 3. 界面总览

### 3.1 顶栏

```text
TraceSphere RCA Console ｜ 01 拓扑 ｜ 02 健康 ｜ 03 告警 ｜ 04 诊断 ｜ 环境标识 ｜ 数据源徽标 ｜ 数据源切换
```

| 元素 | 说明 |
|---|---|
| `01 拓扑` | 资源拓扑 |
| `02 健康` | 健康总览（默认页） |
| `03 告警` | 告警列表；有未处理告警时显示数字角标 |
| `04 诊断` | 根因诊断 |
| 环境标识 | 由 `VITE_ENV_LABEL` 配置，例如“ZSvirt 智算云 · 演示环境” |
| 数据源徽标 | `API LIVE` / `FIXTURE REPLAY`；悬停查看请求基址与切换命令 |
| 数据源切换 | 弹出构建期变量说明；切换需要重启 dev server 或重新构建 |

### 3.2 演示路径条

顶栏下方是演示控制条：

| 元素 | 说明 |
|---|---|
| 演示路径 | 四个场景按钮：容器 OOM、CPU 争抢、工具失败、GPU 显存耗尽 |
| 当前场景 | 显示 `correlation_id`、规则 ID 与场景提示 |
| 刷新 | 立即重新取数 |
| 自动 20s | 每 20 秒自动刷新 |

切换场景会：

- 把 `scenario`、`correlation_id` 或 `resource_id` 写入 URL；
- 拓扑页聚焦该场景的焦点资源；
- 诊断页自动填入 `correlation_id` 并执行；
- 告警页给对应告警加“当前场景”标记。

### 3.3 页脚

页脚显示：

- 最近取数时间（UTC）；
- API 基址；
- 来源状态条：`platform: 真实 / prometheus: 真实 / fixture: 回放`；
- 版本与赛事标识。

来源状态条是判断“数据是真实还是回放”的第一入口。

### 3.4 颜色与标签

| 类别 | 取值 | 含义 |
|---|---|---|
| 健康状态 | 健康 / 警告 / 严重 / 未知 | 资源与工作负载状态 |
| 证据严重度 | 提示 / 警告 / 重要 / 严重 | `info / warning / major / critical` |
| 证据层级 | 应用层 / 容器层 / 虚拟机层 / 云平台层 | `application / container / vm / zsvirt` |
| 告警状态 | 未处理 / 已确认 / 已恢复 / 已静默 | `open / acknowledged / resolved / silenced` |
| 来源类别 | cgroup v2 / eBPF / 指标 / 应用事件 / 日志 / ZSvirt / 拓扑 | 证据来自哪里 |

状态色只表达健康语义：绿=健康、橙=警告、红=严重、灰=未知。层级色用于时间线：应用蓝、容器青、虚拟机紫、云平台褐。

## 4. 核心概念

### 4.1 资源标识

格式：`<kind>:<key>`。

| 示例 | 含义 |
|---|---|
| `host:<uuid>` | 宿主机 |
| `vm:<uuid>` | 虚拟机 |
| `container:<64位id>` | 容器 |
| `service:<name>` | AI 服务 |
| `task:<task_id>` | Agent 任务 |
| `process:<pid>:<start_time>` | 进程 |
| `gpu:<uuid>` | GPU（Mock 模式为 `gpu:mock-gpu0`） |

### 4.2 correlation_id

一次 Agent 任务的应用层关联锚点。agent-service 每次 `/task` 生成一个 12 位 ID，任务内的 `task.started / tool.call / tool.result / inference.result / task.failed / task.finished` 都带同一个 `correlation_id`。

用法：

- 在诊断页输入 `correlation_id`，查看这次任务相关的全部证据；
- 在告警列表搜索 `correlation_id`，定位对应告警；
- 在 URL 中直接传 `?correlation_id=...`。

### 4.3 Evidence（证据）

证据是平台从原始事件中归一化出的结构化事实，关键字段：

| 字段 | 说明 |
|---|---|
| `evidence_id` | 证据 ID，可逐条引用 |
| `signal` | 归一化信号名，如 `memory.events.oom_kill` |
| `kind` | cgroup / ebpf / metric / app_event / log / zsvirt / topology |
| `layer` | application / container / vm / zsvirt |
| `resource_id` / `resource_name` | 证据落在哪个资源 |
| `observed_at` | 观测时间（UTC） |
| `severity` | info / warning / major / critical |
| `description` | 人类可读描述 |
| `value` / `unit` | 数值与单位 |
| `source_event_ids` | 原始事件 ID，可回溯 |
| `mode` | real / mock |

### 4.4 Incident（告警）

一个关联簇 + Top-1 诊断摘要 = 一条告警。告警不是“单条指标越界”，而是“多条跨层证据被判定为同一次故障”。

告警状态：

```text
open（未处理） → acknowledged（已确认） → resolved（已恢复）
       ↘ silenced（静默） ↗
```

状态写入 RCA 的 JSON 文件，重启后保留；不依赖外部 Alertmanager。

### 4.5 Evidence Match

规则证据命中评分，0–100，**不是概率，也不是准确率**。五个维度：

| 维度 | 上限 | 含义 |
|---|---:|---|
| 规则证据命中 | 55 | YAML 条款命中了多少 |
| 时间优先性 | 15 | 根因信号是否早于业务失败；规则没有 `after` 时该维度不适用 |
| 资源邻接度 | 10 | 证据是否在同一资源 / 同一 VM / 图邻接 |
| 信号强度 | 10 | 主证据严重度与额外证据数 |
| 独立证据数 | 10 | 覆盖了多少类证据来源 |

总分按“适用维度上限”归一化。规则没有时序约束时，分母是 85 而不是 100，所以子项相加看起来不等于总分，这是设计行为。

### 4.6 health_score

健康页工作负载卡片上的 0–100 展示分，由证据严重度与指标阈值综合得出。它只用于排序与展示，**不参与 RCA 评分**。

## 5. 资源拓扑

路由：`/topology`

### 5.1 用途

从 ZSvirt 五层资源关系看“谁承载谁”：

```text
宿主机 → 虚拟机 → 容器 → 服务 → Agent 任务
```

GPU 降级模式下额外显示：

```text
宿主机 → GPU → 虚拟机
```

### 5.2 顶部汇总

| 卡片 | 含义 |
|---|---|
| 资源总数 | 拓扑节点总数 |
| 健康 / 警告 / 严重 / 未知 | 各状态资源数 |
| 关联告警 | 告警总数与未处理数 |

### 5.3 画布操作

| 操作 | 方法 |
|---|---|
| 平移 | 拖拽画布 |
| 缩放 | 滚轮，或右下角 `+` / `-` |
| 适应画布 | 右下角“适应画布”按钮 |
| 查看详情 | 点击节点，打开右侧 Drawer |
| 聚焦资源 | 顶部“聚焦某资源”下拉，支持搜索 |
| 切换层级 | `L1 云平台` / `L2 工作负载` / `L3 进程` |
| 资源种类过滤 | 工具栏下拉，按宿主机 / VM / 容器 / 服务 / 任务 / GPU 过滤 |

层级说明：

- **L1 云平台**：只显示宿主机、VM 等骨架；
- **L2 工作负载**：展开容器、服务、任务；
- **L3 进程**：追加进程层，仅在采集到 `process` 节点时有内容。

### 5.4 节点 Drawer

点击节点后显示：

- 状态、资源 ID、名称、副标题（如 IP、规格）；
- 工作负载健康分、任务失败数、最近事件时间；
- 指标（如 CPU、内存、限流）；
- 相关事件（当前时间窗）；
- 关联告警；
- 邻接资源，可继续点击跳转。

### 5.5 侧栏

| 区块 | 用途 |
|---|---|
| 告警资源 | 当前有告警的资源列表，点击聚焦 |
| 最近事件 | 15 分钟窗口内最近 8 条事件 |
| 演示提示 | 场景切换与层级说明 |

### 5.6 空状态

如果当前真实数据中没有演示场景的焦点资源，页面会显示“拓扑不会假装已聚焦”的提示。这不是错误，而是数据源与场景不匹配；切换到 fixture 构建或选择实际存在的资源即可。

## 6. 健康总览

路由：`/health`（默认页）

### 6.1 用途

先看结论：有多少资源不健康、多少任务失败、哪个工作负载在恶化、事件发生在什么时刻和哪一层。

### 6.2 顶部汇总卡

| 卡片 | 含义 |
|---|---|
| 资源总数 | 拓扑节点总数，含宿主机 / VM / 容器 / 服务 / 任务 |
| 健康 / 警告 / 严重 | 各状态资源数与占比 |
| 任务总数 | 窗口内 agent-service 任务数 |
| 任务失败 | 失败任务数与占比 |
| 告警数 | 告警总数与未处理数 |

### 6.3 工具栏

| 控件 | 选项 | 说明 |
|---|---|---|
| 时间窗 | 15 分钟 / 1 小时 / 6 小时 | 影响汇总、工作负载与时间线 |
| 工作负载过滤 | 全部 / 仅容器 / 仅服务 | 只影响工作负载卡片 |
| 排序 | 按状态严重度 / 按健康分升序 / 按任务失败数 / 按名称 | 默认按状态严重度 |
| 刷新 | 立即取数 | 与顶栏刷新等效 |

### 6.4 工作负载卡片

每张卡片显示：

- 名称、`resource_id`、类型（container / service / vm）；
- `health_score` 与状态标签；
- 父资源链接（如所属 VM）；
- 最多 4 个关键指标：值、阈值、趋势箭头（↑ / ↓ / →）与进度条；
- 异常信号列表：signal、层级、次数、最近时间；
- 任务失败数、最近事件时间；
- 操作：容器显示“诊断”，所有资源显示“拓扑”；
- 当前场景焦点会有“当前场景焦点”标记；
- 有失败任务时提示“建议查看告警详情定位证据链”。

### 6.5 全局事件时间线

- 按层着色：云平台 → 虚拟机 → 容器 → 应用；
- 同一时刻的多层事件合并显示；
- 顶部可按层开关；
- 用于读出“系统层信号在前、应用层表现在后”的因果次序。

### 6.6 空状态

时间窗内没有事件时，会提示切换到更大时间窗，或确认 platform / vm-agent 数据源是否可用。

## 7. 告警列表

路由：`/incidents`

### 7.1 用途

查看所有关联簇及其 Top-1 诊断摘要，按严重度、评分、时间过滤和排序。

### 7.2 汇总卡

| 卡片 | 含义 |
|---|---|
| 告警总数 | 当前列表总数 |
| 严重 / 重要 | 按严重度计数 |
| 未处理 | `open` 状态数量 |
| 受影响任务 | 跨告警求和（去重前） |

### 7.3 过滤与搜索

| 控件 | 说明 |
|---|---|
| 关键字 | 搜索 `incident_id` / `correlation_id` / 标题 |
| 状态 | 全部状态 / 仅未处理 |
| 严重度 | 多选：严重 / 重要 / 警告 / 提示 |
| 规则 | 按规则 ID 过滤，显示每条规则的数量 |
| 时间窗 | 最近 15 分钟 / 1 小时 / 6 小时 / 24 小时，按 `last_seen_at` 过滤 |
| 资源筛选 | 从拓扑或诊断页带 `resource_id` 进入时出现，可一键清除 |
| 刷新 | 立即取数 |

### 7.4 表格列

| 列 | 说明 |
|---|---|
| 严重度 | 告警严重度 |
| 规则 / 标题 | 标题、规则 ID、`incident_id`、`correlation_id`、摘要；当前场景有标记 |
| 重点资源 | 资源名与 `resource_id` |
| Evidence Match | 0–100 分，带进度条；≥80 红色、≥55 橙色 |
| 影响任务 | 受影响任务数 / 证据条数 |
| 首次 / 最近 | 首次与最近发生时间 |
| 状态 | 未处理 / 已确认 / 已恢复 / 已静默，以及来源 |
| 操作 | “详情” |

点击标题或“详情”进入告警详情。

## 8. 告警详情

路由：`/incidents/:id`

### 8.1 页面结构

按“事实 → 诊断 → 证据 → 处置 → 影响”组织：

1. 页头：标题、摘要、严重度、状态、规则、`correlation_id`、时间窗、来源状态；
2. 操作按钮：静默 / 取消静默、确认、标记已处理、返回列表、重新诊断、在拓扑中查看；
3. 汇总卡：证据条数、影响任务、Top-1 评分、候选数、首次发现、最近更新；
4. 事件摘要：Top-1 诊断 + 五维评分明细 + 重点资源 / 根因 / 来源 / 时间窗 / 严重度；
5. 证据列表：命中 Top-1 的证据以 ★ 标注，可展开原始 payload；
6. 处置建议：每条含依据 / 操作 / 风险；
7. 分层时间线；
8. 影响范围：受影响任务、服务、容器，`depth` 表示资源图距离；
9. 备选候选：Top-N 排序语义，点击切换查看（候选数 > 1 时显示）；
10. 相关资源子图：可缩放、适应画布；
11. 指标曲线：仅容器类焦点资源提供，含阈值线。

### 8.2 状态操作

| 当前状态 | 可用操作 | 结果 |
|---|---|---|
| 未处理 | 静默、确认、标记已处理 | `silenced` / `acknowledged` / `resolved` |
| 已确认 | 静默、标记已处理 | `silenced` / `resolved` |
| 已静默 | 取消静默、标记已处理 | 恢复 `open` / `resolved` |
| 已恢复 | 静默 | `silenced`（再次静默） |

操作成功后页面刷新并提示。状态写入 RCA 的 `data/silenced.json`，重启后保留。

> “静默”只改变运营状态，不删除证据，也不影响后续诊断。

### 8.3 证据阅读

- 每条证据显示 `evidence_id`、`signal`、来源类别、层级、资源、时间、描述；
- 展开后可见 `evidence_id`、`observed_at`、`layer / kind`、`resource`、`correlation_id`、`task_id`、`source_event_ids`、`mode` 与原始 payload；
- `source_event_ids` 可回到平台 `/api/v1/events` 查原始事件；
- ★ 表示该证据被当前 Top-1 候选引用；
- 证据为空时，页面会提示数据源被禁用或窗口内无异常，不会伪造内容。

### 8.4 影响范围

- `counts.tasks / services / containers` 给出数量；
- `scope` 列表显示资源、类型、关系、`depth`、状态；
- `depth=1` 通常是一跳邻接，`depth=2` 是影响范围扩展；
- 点击“拓扑”跳转到拓扑页并聚焦该资源。

### 8.5 指标曲线

- 仅容器类资源提供；
- 曲线带阈值线（如内存上限、PSI 阈值）；
- 焦点资源不是容器时显示“仅容器类资源提供曲线”的说明；
- 指标数据来自 Prometheus / cAdvisor；不可用时显示错误与处理提示。

## 9. 根因诊断

路由：`/diagnosis`

### 9.1 用途

对指定锚点与时间窗执行规则匹配，输出按 Evidence Match 降序的根因候选 Top-N。

### 9.2 输入

| 控件 | 说明 |
|---|---|
| 锚点类型 | `correlation_id`（一次 Agent 任务）或 `resource_id`（系统层资源） |
| 输入框 | `correlation_id` 示例 `d38fc66c8364`；`resource_id` 必须带类型前缀，如 `container:7196bcad3bc1` |
| 时间窗 | 15 分钟 / 1 小时 / 6 小时 |
| Top-N | 1–5 条 |
| 示例输入 | 四个场景各提供 `correlation_id` 与 `resource_id` 快捷按钮 |
| 执行诊断 | 提交请求 |

输入校验：

- 空值会提示“请输入关联锚点 / 资源标识”；
- `resource_id` 不含 `:` 时提示“资源标识应包含类型前缀”。

### 9.3 结果区

| 区块 | 内容 |
|---|---|
| 汇总卡 | 候选根因数、参与评分证据数、Top-1 评分、时间窗、影响任务数 |
| 根因候选 Top-N | 标题、严重度、Evidence Match、根因标识、规则版本；点击切换候选 |
| 五维评分 | 规则证据命中、时间优先性、资源邻接度、信号强度、独立证据数；每项含分数 / 上限 / detail |
| 处置建议 | 当前候选的 `result.suggestions`，每条含依据 / 操作 / 风险 |
| 引用证据 | 当前候选的 `evidence_ids`，★ 标出命中证据 |
| 候选排序 | 点击某条候选查看完整明细 |
| 影响范围 | 受影响任务与资源；可跳转拓扑 |
| 分层时间线 | 诊断窗口内的事件 |

### 9.4 如何解读

1. **先看 Top-1 是否命中你预期的层级**：容器 / VM / 应用；
2. **再看五维明细**：如果 `rule_match` 低，说明关键证据缺失；如果 `temporal_precedence` 为 0/0，说明规则没有时序约束；
3. **对照证据 ID**：每条结论都能在证据列表中找到；
4. **看 `sources.notes`**：平台不可用时会注明补入了多少条 fixture 证据；
5. **不要把分数当概率**：99 分表示证据命中充分，不表示 99% 概率；
6. **没有结果时**：先确认窗口内是否有事件、数据源是否可用、锚点是否正确。

### 9.5 规则库

页面底部展示 `GET /api/v1/rules` 返回的四条规则：

- `container_oom`
- `cpu_contention`
- `tool_failure`
- `gpu_memory_exhaustion`

点击规则按钮可聚焦查看；卡片内展示条款权重、`after` 约束，并提供可展开的 `rule / evidence / correlation / result` YAML 结构与处置建议。新增规则只需新增 YAML，不需要改引擎代码。

## 11. 命令行（CLI）

### 11.1 构建

```bash
cd rca
go build -o bin/tracesphere ./cmd/tracesphere
```

### 11.2 常用命令

```bash
# 服务 + Console
./bin/tracesphere serve --listen :8010 --console ../console/dist

# 诊断
./bin/tracesphere diagnose --correlation-id <corr> --window 10m
./bin/tracesphere diagnose --resource-id container:<id> --window 10m
./bin/tracesphere diagnose --scenario case1-oom

# 告警 / 健康 / 拓扑 / 规则
./bin/tracesphere alerts --window 10m
./bin/tracesphere alerts --severity critical --rule container_oom
./bin/tracesphere health --window 15m
./bin/tracesphere topo --focus container:<id>
./bin/tracesphere rules

# JSON 输出（脚本用）
./bin/tracesphere diagnose --scenario case1-oom --json
./bin/tracesphere alerts --json
```

### 11.3 环境变量

| 变量 | 默认 | 说明 |
|---|---|---|
| `TRACESPHERE_PLATFORM_URL` | `http://127.0.0.1:8000` | 平台地址 |
| `TRACESPHERE_PLATFORM_TOKEN` | 空 | 平台 Token |
| `TRACESPHERE_PROMETHEUS_URL` | `http://127.0.0.1:9090` | Prometheus 地址 |
| `TRACESPHERE_RCA_FIXTURE` | 空 | `1` 强制 fixture |
| `TRACESPHERE_RCA_SCENARIO` | 空 | fixture 场景 |

### 11.4 输出阅读

`diagnose` 文本输出包含：

- 时间窗与数据源；
- `correlation_id` / `resource_id`；
- `[1]` Top-1 标题、Evidence Match、规则版本、严重度；
- 根因与说明；
- 五维评分明细；
- 证据列表（ID、signal、kind、资源、时间、值）；
- 处置建议；
- 备选候选；
- 注：Evidence Match 为规则证据命中评分，非概率。

`--json` 输出与 [API.md §4.5](../rca/docs/API.md) 的 Diagnosis 对象一致。

## 12. 数据源与真实性标识

### 12.1 两种构建模式

| 模式 | 徽标 | 数据来源 | 适用场景 |
|---|---|---|---|
| api | `API LIVE` | RCA `/api/v1` | 真实环境 / 联调 |
| fixture | `FIXTURE REPLAY` | `src/mocks/*.json` | 无后端演示 / 录屏 |

模式由 `VITE_DATA_SOURCE` 在构建期决定，运行时只读。切换需要重启 dev server 或重新构建。

### 12.2 为什么 api 模式失败不自动降级

这是刻意设计：评审 / 运维必须能一眼区分“真实数据”和“回放数据”。api 模式请求失败时页面显示：

- 请求路径；
- HTTP 状态；
- 处理指引；
- 切换到 fixture 的命令。

不会静默换成夹具。

### 12.3 来源状态

页脚 / 页头显示：

- `platform: 真实 / 降级 / 未启用`；
- `prometheus: 真实 / 降级 / 未启用`；
- `fixture: 回放 / 未启用`。

诊断响应还会在 `sources.notes` 中说明补入了多少条证据。阅读结论前先看来源状态。

## 13. 常见任务

### 13.1 调查一次 Agent 任务失败

1. 从 agent-service 返回或日志中拿到 `correlation_id`；
2. 打开诊断页，选择 `correlation_id`，输入 ID，时间窗选 15 分钟；
3. 看 Top-1 是否命中；看五维明细哪一项缺失；
4. 打开引用证据，确认 `signal`、资源、时间；
5. 如果证据不足，切到告警列表搜索该 `correlation_id`，查看是否有完整关联簇；
6. 按处置建议操作，并在告警详情中标记“确认 / 已处理”。

### 13.2 从告警定位到拓扑

1. 告警详情页点击“在拓扑中查看”；
2. 拓扑页会聚焦 `focus_resource`；
3. 在 Drawer 中查看邻接资源、相关事件、指标；
4. 如需查看上层影响，切换 L1 / L2。

### 13.3 确认某个容器是否异常

1. 健康页筛选“仅容器”，按“任务失败数”或“健康分”排序；
2. 点击卡片上的“诊断”，直接带 `resource_id` 进入诊断页；
3. 或点击“拓扑”，查看其父 VM 与邻接服务。

### 13.4 查看告警运营状态

1. 告警列表按“仅未处理”过滤；
2. 进入详情，执行“确认”或“标记已处理”；
3. 静默适合已知演练窗口；静默不会删除证据；
4. 取消静默后恢复 `open`。

### 13.5 回放一个场景

1. 顶栏“演示路径”选择场景；
2. 健康 / 拓扑 / 诊断会自动带 `correlation_id` / `resource_id`；
3. 若在 fixture 构建中，所有页面直接使用夹具；
4. 若在 api 构建中，需要该场景的真实数据存在；否则页面会提示无焦点资源。

## 14. 常见问题

| 问题 | 原因 | 处理 |
|---|---|---|
| 页面打不开 | RCA 未启动 / 端口不对 / 反向代理未配置 | 检查 `systemctl status tracesphere-rca`、`curl http://<host>:8010/` |
| 页面 401 | RCA 启用了 Token | 用 `?token=<RCA_TOKEN>` 重新打开 |
| 页面显示“无法连接诊断服务” | api 模式请求失败 | 检查 8010、`VITE_RCA_BASE_URL`、网络；或切到 fixture 构建 |
| 数据源徽标一直是 FIXTURE | 构建时设置了 `VITE_DATA_SOURCE=fixture` | 重新用 api 模式构建 |
| 诊断无结果 | 窗口内无证据 / 数据源禁用 / 锚点错误 | 放宽时间窗；检查 health 的 sources；核对 ID |
| 证据列表为空 | 关联簇无证据或来源被禁用 | 查看 `/api/v1/health` 与 `sources.notes` |
| 告警列表为空 | 没有关联簇 / 时间窗过窄 | 放宽到 24 小时；确认场景已注入 |
| 分数子项相加不等于总分 | 规则没有时序约束，分母为 85 | 这是归一化设计，见 §4.5 |
| 时间显示与本地不一致 | 页面统一 UTC | 换算本地时区；检查节点 NTP |
| 拓扑没有进程层 | 未采集到 `process` 节点 | `VMAGENT_REPORT_PROCESS=1` 后重启探针 |
| 拓扑没有 GPU | 未启用 mock_gpu 或数据源是真实 ZSvirt 无 GPU | 平台开启 `TRACESPHERE_MOCK_GPU=1`；确认 mock-dcgm 运行 |
| 指标曲线为空 | 焦点资源不是容器 / Prometheus 不可用 | 切换到容器；检查 `PROM_BIND` 与 9090 |
| 告警状态重启后丢失 | `silenced.json` 路径不可写 | 检查 RCA 工作目录与 `data/` 权限 |
| fixture 模式下 6h 窗口数据很少 | 夹具只覆盖约 15 分钟，时间平移到最近 | 这是预期行为 |
| 页面右上角告警角标不消失 | 还有 `open` 状态告警 | 在详情页确认 / 处理 |

## 15. 使用边界

1. **Evidence Match 不是概率**：99 分是证据命中充分，不是 99% 准确率；项目没有做概率校准。
2. **health_score 只用于展示**：不参与 RCA，不要拿它和 Evidence Match 比较。
3. **四场景是受控结果**：99 / 85 / 67 / 89 只适用于对应受控故障与采集配置，不是通用准确率。
4. **Case3 的边界**：2026-09-30 验收中证据全部是应用事件，没有传输层证据；工具失败结论仍成立，但不要把它表述为“已证明网络传输异常”。
5. **Case4 的边界**：Mock DCGM 是降级数据源，指标名为 `ts_gpu_*`，语义兼容但不是真实 DCGM；没有真实 GPU 验证。
6. **只读 ZSvirt**：platform 不调用 ZSvirt 写接口；这由代码保证，不是账号权限限制。
7. **告警能力边界**：没有 Alertmanager；当前是自研关联簇聚合 + 三态运营 + 静默，不包含分组 / 抑制 / 通知渠道。
8. **Console 无用户体系**：只有静态 Token，没有角色与审计；生产多用户需外层 SSO / 反向代理。
9. **数据保留**：平台 SQLite 单文件；重置数据库会丢失历史证据，演示前请备份。

## 16. 术语表

| 术语 | 说明 |
|---|---|
| Agent 任务 | agent-service 执行的一次“工具调用 + 推理”流程 |

| 降级模式 | 数据源或采集能力不可用时的可用路径 |
| spool | vm-agent 上报失败时的本地重试队列 |
